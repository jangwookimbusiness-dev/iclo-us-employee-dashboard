# 청구로 확인하는 예방 진료 프로그램

**미국 기업의 치과 복리후생을 위한 예방 진료 프로그램입니다.**

임직원은 스마트폰으로 2분 구강 체크인을 하고 보장 내용을 안내받습니다. 기업은 그 참여가
실제 예방 진료로 이어졌는지를 자체 청구 데이터로 확인합니다. 임직원 개인은 본인의 정보만
보며, 기업에는 집계 결과만 제공됩니다.

시장은 두 단계로 접근합니다. 자기부담(self-funded) 기업에서는 진료 이용의 변화가 그해
청구 비용에 직접 반영됩니다. 완전보험(fully-insured) 기업에서는 같은 프로그램의 결과가
갱신 협상의 근거가 됩니다(§7.1a). 첫 PoC는 자기부담 기업에서 진행합니다. 캐리어의 근거
인정에 의존하지 않아 가장 짧은 기간에 검증할 수 있기 때문이며, 대상 시장을 자기부담으로
한정한다는 뜻은 아닙니다(§8).

## 0. 제안 개요

제안하는 것은 별도의 조회 화면이 아니라, 임직원 참여에서 청구 확인까지 이어지는 예방
진료 프로그램입니다.

미국의 자기부담 기업은 임직원 치과 청구를 자기 계좌에서 지급하면서도, 예방 진료 이용을
유도하고 그 결과를 적시에 확인할 수단이 없습니다. 통상 연 1회 제공되는 TPA 보고서는 이미
발생한 진료와 비용을 사후에 정리한 자료입니다. 조회 화면만 추가해서는 이 무료 보고서와
기능이 중복됩니다.

프로그램은 네 단계를 연결합니다.

```
신호    임직원이 스마트폰으로 구강을 촬영 → 밴드(Low · Moderate · Priority)
권고    Priority인 경우 진료 권고 제공 — 강제 없음, opt-in
행동    보장 안내 · 인네트워크 치과 · 예약 연결 · 리마인더
확인    몇 주 뒤 동일인의 청구로 방문을 확인 — 청구로 확인된 경우만 완료로 집계
```

차별점은 마지막 확인 단계에 있습니다. 완료 여부를 참여자의 자가 보고가 아니라 **기업
자체의 청구 데이터**로 확인합니다. 이를 위해 자격·앱 활동·청구 데이터를 개인 단위로
연결하되, 기업에는 집계 결과만 제공해야 합니다. 이 데이터 기반을 Snowflake 위에 구축하는
것이 이번 제안의 핵심입니다.

Snowflake에 요청하는 협력은 두 가지입니다. 첫째, 미국 HLS GTM 담당자·아키텍처 담당자와의
연결입니다. 둘째, self-funded 치과 플랜을 운영하는 기업 후보 3곳의 소개입니다. 후보 중
§8의 조건을 충족하는 1곳과 PoC를 진행합니다.

현재 화면은 실행 가능한 상태이며 데이터 계층 설계도 완료되었습니다. 다만 네 단계를 잇는 후속 처리 영역, 곧 Core AI 호출 경로, 리마인더, 예약 연결 백엔드는
아직 구현되지 않았습니다. 항목별 현황은 §9에 정리했습니다.

## 1. 무엇이 달라지는가

복리후생 담당자가 현재 답하기 어려운 질문과, 프로그램 도입 후의 변화입니다.

| 질문 | 현재 | 도입 후 |
|---|---|---|
| 임직원 구강 상태의 분포 | 파악 불가 — 청구는 이미 진료받은 사람만 반영 | 신호 분포를 진료 전에 확인 |
| 예방 진료 미이용 인원 규모 | 집계 자료 없음 | 부서 단위 집계로 확인, 개인은 비노출 |
| 권고한 진료의 실제 이행 여부 | 연결 자체가 불가능 | 청구로 확인된 완료 건수 |
| 분기 비용의 흐름 | 연 1회 보고서 대기 | 청구 도착분까지 기준일과 함께 확인 |

세 번째 항목이 이 프로그램의 핵심입니다. 앱 활동만으로는 자가 보고에 그치고, 청구만으로는
권고와의 연결을 알 수 없습니다. 두 데이터를 같은 사람으로 연결해야 "청구로 확인된 완료"가
성립하며, 청구와 자격 정보만 가진 TPA 보고서는 이 연결을 만들 수 없습니다.

다만 이 확인은 진료가 이루어졌다는 사실의 확인이며, 인과관계의 입증이 아닙니다. 권고
후 진료가 이루어졌더라도 원래 예정된 진료였는지는 이 데이터로 구별할 수 없습니다.
인과를 말하려면 대조군 설계가 필요하고, 그 설계는 아직 없습니다. 따라서 화면과 문서
어디에도 "절감"이나 "효과"라는 표현을 쓰지 않습니다. 완료 건수를 집계하되 기여도는
주장하지 않습니다.

네 번째 항목의 수치는 전제를 두고 해석해야 합니다. 청구 지연은 중앙값 45일, 롱테일
180일로 설정했습니다. 이는 업계 통상 범위이며 자체 실측값이 아닙니다. 실데이터가 들어오면
첫 분기에 이 분포부터 측정합니다. 단축되는 것은 데이터 처리 구간이며, 진료에서 청구까지의
시간은 프로그램이 줄일 수 없습니다. 따라서 자격 기준일과 청구 기준일을 화면에 분리해 표시합니다.

## 2. 임직원 화면

프로그램의 성패는 임직원 참여에 달려 있습니다. 참여가 없으면 신호가 생성되지 않고,
권고·확인·기업 화면 모두 성립하지 않습니다. 따라서 임직원 화면은 감시 도구가 아니라
복지로 받아들여지도록 설계했으며, 아래 화면들이 그 설계입니다.

화면은 실제로 동작하며, 현재는 합성 데이터로 구동됩니다. 화면 코드에는 회원 데이터가
포함되어 있지 않습니다. 계정·플랜·보장률·치과·동의 정보는 화면 밖의 데이터 파일 한 곳에서
읽으며, 실데이터 전환 시 이 파일의 형식이 백엔드 응답 규격이 됩니다. 데이터 교체만으로 해결되지 않는 Core AI 호출, 급여 게이트웨이, 네트워크 디렉터리, 예약
항목은 §9에 있습니다.

### 2.1 검진은 폰으로, 결과는 본인만

사람, 계정, 대리 권한을 각각 다른 계층으로 관리합니다.

```
credential ──N:M── profile_access ──N:M── party
 (로그인)          (SELF | GUARDIAN)      (사람)
```

<img src="assets/app-home.png" width="215" style="float:left;margin:4px 20px 10px 0">

`party`와 `credential` 어디에도 기업 정보를 두지 않습니다. 한 사람이 두 기업에 동시에
속할 수 있고(부부가 서로를 부양가족으로 등록하는 경우) 이직으로 소속이 바뀌기 때문입니다.
기업을 사람 레코드에 넣으면 구강 이력이 기업 단위로 분리됩니다.

성인 가족은 이 계정에 연결되지 않습니다. 본인 기기에서 본인이 동의합니다. 임직원이
배우자의 동의를 대신하면 그 처리의 법적 근거가 무효가 될 수 있어, 화면에도 해당 기능을
의도적으로 두지 않았다고 안내합니다.

개인에게 점수 숫자를 제공하지 않습니다. 밴드와 변화 방향만 표시합니다. 점수는 내부
계산에만 사용하며, **FDA clearance 전까지** 이 원칙을 유지합니다.

촬영 대상은 매번 새로 선택하며, 계정 소유자도 기본값으로 두지 않습니다. 공유 기기에서
직전 프로필이 유지되는 것이 사진이 다른 사람에게 귀속되는 가장 흔한 경로이기 때문입니다.

이 오류는 집계 화면에 드러나지 않습니다. 화면은 정상으로 보이고 청구 연결만 다른 사람을
가리키게 됩니다. 완료 확인이 동일인의 청구를 전제로 하는 프로그램에서 이 오귀속은 확인
자체의 신뢰성을 훼손하므로, 다섯 가지 방어를 둡니다 — 매번 선택, 자동 선택 금지, 대상자
이름의 최대 표시, 이탈 시 프로필 해제, 촬영자와 대상의 분리 기록.

마지막 항목이 특히 중요합니다. 한 로그인이 3분 안에 다섯 명을 촬영한 기록은 가족 검진일
수도, 오조작일 수도 있습니다. 두 정보를 모두 남겨야 사후에 구별할 수 있습니다.

신호가 나오면 보장 내용과 가까운 인네트워크 치과 정보로 연결합니다. 확인에서 실제 예약
사이의 거리를 줄이는 단계입니다.

잔여 연간 한도는 의도적으로 표시하지 않습니다. 보유한 데이터는 이미 접수된 청구뿐이고
청구는 수 주 늦게 도착하므로, 최근 진료를 반영하지 못한 잔여액을 표시하면 실제 잔여가
없는 사람이 보장이 남았다고 믿고 치과를 방문하게 될 수 있습니다. 정확한 출처는 X12
270/271 실시간 급여 조회이며 아직 연동 전입니다. 연동 전까지는 숫자 대신 TPA 조회 링크를
제공합니다. 기술 설계 문서도 이를 타협 불가 항목으로 규정하고 있습니다.

예약은 임직원이 치과와 직접 진행합니다. 치과의 일정 정보를 보유하지 않으므로 빈 시간대를
표시하지 않습니다. 예약 완료 여부는 사후에 확인하며, 그 응답은 자가 보고로 분류되고 완료
집계에는 포함되지 않습니다. 완료는 수 주 뒤 청구로만 확정됩니다.

### 2.4 동의는 사람별·목적별

<img src="assets/app-settings.png" width="215" style="float:left;margin:4px 20px 10px 0">

`데이터 처리`, `사진 촬영과 분석`, `청구 연결`을 각각 켜고 끌 수 있습니다. 사진에는
동의하되 청구 연결은 거부하는 선택이 실제로 존재하며, 단일 스위치로는 표현할 수 없습니다.
청구 연결을 거부한 사람은 완료 확인 단계에서 제외될 뿐, 다른 기능은 그대로 사용합니다.

동의는 스위치 값이 아니라 기록으로 관리합니다. 목적, 시각, 동의한 정책 문안의 버전이
함께 남고 삭제되지 않습니다. 단순 참/거짓 모델이 표현하지 못하는 상태가 세 가지 있으며,
모두 실제로 발생합니다.

| 상태 | 참/거짓 모델의 해석 | 실제 처리 |
|---|---|---|
| 동의 후 정책 문안이 개정됨 | 계속 동의 상태 | 재동의 필요 상태로 전환 |
| 동의 후 철회함 | 거부 상태 | 거부 + 당시 허용 범위의 증거 보존 |
| 동의를 요청한 적 없음 | 거부 상태 | 거부와 구별해 관리 |

첫 번째 상태가 가장 중요합니다. 참/거짓 모델은 개정된 문안 아래에서 처리를 계속하게
됩니다. 이 시스템은 정책 버전이 올라가면 이전 동의의 효력을 중지하고 화면에 재동의
필요로 표시합니다.

동의는 촬영 직전에 평가합니다. 가입 시점의 플래그를 읽지 않으며, 철회·미동의·구버전 동의
모두 촬영을 차단합니다. `데이터 처리`를 철회하면 `사진` 동의가 남아 있어도 촬영이
차단됩니다. 사진 처리가 데이터 처리 동의를 전제로 하기 때문입니다. 네 가지 차단 경우는 자동으로 검사합니다.

철회는 이후의 처리를 중지합니다. 이미 배포된 집계의 재생성 여부는 아직 결정 전이며,
화면에도 그렇게 표시합니다. 사진 보존 일정은 결정되었고 아직 운영 전입니다 — 사진
24개월, 파생 신호 7년, 동의 기록 영구 보존이며, 삭제는 해당 개인의 암호화 키를 파기하는
방식으로 모든 사본을 동시에 읽을 수 없게 합니다. 저장소 구축 전이므로 현재 이 정책을
강제하는 시스템은 없습니다.

## 3. 기업 화면

기업 화면의 수치는 모두 프로그램 참여에서 생성됩니다. 참여가 없으면 기존 TPA 보고서와
같은 내용만 남고, 참여가 있으면 TPA 보고서가 구조적으로 제공할 수 없는 두 항목 — 진료 전
신호 분포, 청구로 확인된 완료 — 이 추가됩니다.

### 3.1 `Program overview` — 참여와 비용, 분모의 분리

![기업 대시보드 개요](assets/dashboard-overview.png)

이 화면의 원칙은 분모의 분리입니다. 참여는 자격자 수로, 비용은 가입자-월로 집계하며 두
분모는 한 지표 안에서 섞이지 않습니다. 렌즈 토글이 현재 화면이 어느 분모 위에 있는지
표시합니다.

각 수치에는 출처 칩이 붙습니다. 칩을 열면 해당 값이 어느 피드에서 오는지 확인할 수
있습니다. 현재 화면 값은 합성 데이터이므로 칩은 실적재 시의 경로를 사전에 정의한
계약이며, 파이프라인 연결 후에는 실제 적재 시각과 배치 ID를 표시하게 됩니다.

### 3.2 개인 비노출 — 한 번의 조회 기준

![억제가 걸린 화면](assets/dashboard-suppressed.png)

부서를 좁혀 20명 미만이 되면 지표가 숨겨지고 사유가 표시됩니다. 그룹 크기는 억제 안내문이
이미 공개하는 정보이므로 분모는 남습니다.

담당자가 특정 개인을 식별할 수 있게 되는 순간 이 프로그램은 인사 도구로 인식되고,
임직원 참여가 중단됩니다. §2 서두에 적었듯 참여가 없으면 프로그램 전체가 성립하지
않으므로, 개인 비노출은 윤리 조항이 아니라 사업의 성립 조건입니다.

정확성을 위해 "절대 노출되지 않는다"고 쓰지 않습니다. 최소 그룹 크기는 한 번의 조회
안에서 성립하는 보호이며, 조회를 나누면 차분이 남습니다.

```
영업부 전체            24명 · Priority 6명
영업부 중 2년 이상     23명 · Priority 5명
────────────────────────────────────────
차이 1명 — 두 조회 모두 최소 20명 기준을 통과
```

이에 대해 네 가지 방어를 설계했습니다. 기술 설계 문서 11.3절에 상세가 있습니다.

| | 방어 | 비용 |
|---|---|---|
| 1 | 조회 축 제한 — 화면이 부서·월만 제공 | 없음. 현재 성립 |
| 2 | 인접 억제 — 이웃 셀과의 차이가 20명 미만이면 양쪽 모두 숨김 | 억제 범위가 넓어져 소규모 기업에서 표시 항목 감소 |
| 3 | 조회 이력 검사 — 24시간 내 포함 관계 재요청 거부·기록 | 내보내기 기록 계층 필요, Enterprise 에디션 |
| 4 | 조합 한도 — 롤·30일당 200개 초과 시 보류 후 검토 | 오탐 가능, 자동 차단 대신 검토 |

네 가지를 겹쳐도 완전한 방어는 아니며, 문서에도 그렇게 기재합니다. 이 설계의 목적은
공격 비용을 높이고 기록을 남기는 것입니다.

왼쪽이 진료 전 신호 분포, 오른쪽이 청구로 확인된 완료입니다. 신호 라벨은 `Low ·
Moderate · Priority`이며 질환명을 사용하지 않습니다. 일반 웰니스 범위 안에 남기 위한
선택이고, `Priority`의 설명문도 "general dental consult suggested — not a clinical
finding"입니다. 이 판단의 근거와 한계는 §10.4에 있습니다.

분포는 촬영 건수가 아니라 사람 수를 집계합니다. 한 사람당 최근 12개월 내 유효 촬영 중
최신 1건만 반영하므로, 매달 촬영한 사람이 열두 배로 집계되지 않고 퍼널의 전후 단계와
분모가 일치합니다.

퍼널의 마지막 행은 청구로 확인된 완료만 집계하며, 자가 보고는 성과에 포함하지 않습니다.

## 4. 데이터 보호 설계

기업 보안 검토에서 나올 질문들에 대한 답입니다. 통제는 화면 코드가 아니라 데이터 계층에
있어야 한다는 원칙으로 설계했습니다.

이 절은 설계이며 현재 운영 상태가 아닙니다. 아래 통제는 DDL 수준까지 작성되었고 아직
실행 전입니다. 현재 데모의 억제는 화면 코드가 수행하며, §6의 1단계가 이 절의 통제를 실제
Snowflake 오브젝트로 구축하는 작업입니다.

### 4.1 신뢰 경계

```
  개인 레벨 데이터는 존재한다  ─┐
  사진 · 신호 · 방문 · 청구      │  ICLO 내부에만
  전부 사람 단위로 저장된다     ─┘

  기업이 보는 것은 집계다
  최소 셀 20명(고유 인물) · 밴드 · 부서 필터
```

"집계만 저장한다"고 표현하지 않습니다. 완료 확인은 앱 활동과 청구를 같은 사람으로
연결해야 성립하므로 개인 단위 저장은 불가피합니다. 정확한 표현은 "기업이 볼 수 있는
범위를 데이터 계층에서 제한한다"입니다. 화면 코드의 억제는 화면을 수정하면 풀리기
때문입니다.

### 4.2 `ENTITY KEY` — 고유 인물 수 집계

최소 그룹 크기는 기본적으로 행 수를 셉니다. 한 사람이 청구 라인을 20개 만들면 그룹 크기
20을 충족하므로, 실제로는 1명인 집계가 기업 화면에 노출될 수 있습니다. `ENTITY KEY
(party_sk)`를 지정해야 고유 인물 수로 집계합니다.

이 결함은 데모에서 드러나지 않습니다. 데모의 억제는 화면 코드가 사람 수로 판정하기
때문이며, 실데이터 전환 시점에 조용히 약화되는 유형입니다. 검증은 §6의 1단계에서 합성
3사 데이터로 수행합니다. 결함의 성립 조건은 테이블 구조와 DDL뿐이어서 데이터의 실제
여부와 무관하고, 판정도 이분법입니다 — 고유 인물 1명인 그룹이 값으로 반환되면 결함,
잔여 그룹으로 접히면 정상.

이와 별개로 합성 데이터로 검증할 수 없는 결함이 하나 더 있습니다.

| | 오류 유형 | 검증 방법 |
|---|---|---|
| `ENTITY KEY` 부재 | 행을 사람으로 집계 | 합성 데이터로 완전 검증 |
| 신원 해석 품질 | 한 사람을 여러 명으로 집계 | 실데이터 필요 |

자격 파일과 청구를 연결하는 매칭이 한 사람을 두 레코드로 분리하면, 최소 20명 기준이
실제로는 더 적은 인원에서 통과되어 보호가 약화됩니다. 합성 데이터는 식별키가 정답으로
생성되므로 이 문제를 드러낼 수 없습니다. PoC 파트너 데이터 확보 후 첫 주에 확인할
항목이며, 매칭률은 품질 지표로 주간 보고합니다.

### 4.3 그 외 통제

행 접근 정책이 기업 간 격리를, 마스킹 정책이 생년월일 등 매칭용 필드의 차폐를, 접근
이력이 조회 감사를 담당합니다. 접근 이력은 Snowflake 내부만 기록하므로, 사진 저장소·추론
호출·관리자 이벤트를 공통 요청 ID로 연결하는 감사 모델을 별도로 설계에 포함했습니다.

Core AI는 ICLO가 직접 운영합니다. 외부 위탁이 없어 BAA 체인에 제3자가 추가되지 않으며,
추론 API에 감사용 요청 ID를 직접 삽입할 수 있습니다.

## 5. 데이터 흐름

![데이터 흐름](assets/dataflow.svg)

원천은 네 가지입니다 — 기업 또는 benefits administrator가 제공하는 자격 파일(통상 X12
834), TPA의 837D/835, 앱, 임상 파트너. 원천 데이터는 정본 계층에서 개인 단위로 연결되고,
노출 계층에는 기업이 볼 수 있는 정보만 남습니다.

그림에는 미구축 항목 여섯 개가 표시되어 있으며, 이 목록은 계약 파일의 미구축 목록과 항목
단위로 일치하도록 관리합니다.

### 5.1 근거 레이어

```
  자격·청구·앱 → RAW_* → STAGED → CANONICAL (20 테이블)
                                        │  내부 롤만 윈도우 함수
                                        ▼
                        mart.person_month_fact   ← party_sk 보유
                          집계 정책 + ENTITY KEY
                          행 접근 정책 · 마스킹
                                        │  기업 롤은 SUM·COUNT만
                        기업별 롤이 각각 내보내기
                                        ▼
                            기업 대시보드
```

정책은 중간 테이블에 적용합니다. 산출물 테이블에는 `party_sk`가 없어 `ENTITY KEY`가
성립하지 않고, 원본 테이블에만 적용하면 버전 선택에 필요한 윈도우 함수가 집계 제약과
충돌합니다. 사람 단위 중간 테이블이 두 문제를 함께 해결합니다.

TPA가 Snowflake를 사용하고 같은 클라우드·리전에 있는 경우 Secure Data Sharing으로 파일
전송 없이 데이터를 받을 수 있으며, 사본이 생기지 않아 데이터 권리 협상이 단순해집니다.
리전이 다르면 복제 과정에서 사본이 생기고, TPA가 Snowflake를 쓰지 않으면 SFTP로
진행합니다.

## 6. 추진 단계

| 단계 | 내용 | 결과 |
|---|---|---|
| 1 | 합성 데이터로 관리형 데이터 계층 구축. 정책·억제·격리를 실제 Snowflake 오브젝트에서 시연 | 거버넌스를 쿼리로 검증 |
| 2 | PoC 파트너 1곳(self-funded) 확정. 착수 차단 게이트 4건 서면 종결 | 실데이터 적재 착수 판정 |
| 3 | 파트너 기업의 자격·청구 데이터로 대시보드 구동 | 첫 결과 보고서 |
| 4 | 결과 보고서 기반으로 브로커 채널 접촉 | 갱신 시즌 진입 |

1단계는 파트너 확정 전에 시작할 수 있으며, 계정과 에디션 확정만 필요합니다.

프로그램의 후속 처리 영역(Core AI 호출 경로, 사진 저장소, 인증)은 위 표와 별도
트랙입니다. 위 표가 검증하는 것은 데이터 계층과 협력 관계이며, 후속 처리는 파트너와
게이트 종결 이후에 구축합니다.

### 6.1 첫 90일의 범위

```
· 미국 HLS GTM·아키텍처 담당자와의 연결, 검증 상대의 확정
· 근거 레이어 아키텍처 설계와 Snowflake 보안 기준 정렬
· 착수 게이트 네 항목의 책임자 지정과 종결 경로 합의
```

실데이터 적재는 이 90일에 포함되지 않습니다. 게이트 4건의 서면 종결 이후에 시작되며,
그 시점은 90일 밖입니다. 따라서 이 기간은 제품 성과가 아니라 협력 관계와 설계의 성립을
검증하는 기간입니다. 기업 약정·계약된 데이터·적재된 청구가 없는 상태에서 제품 성과를
90일에 약속하지 않습니다.

2단계의 게이트 네 건은 HIPAA 역할 규정, 데이터 권리, 동의 이전 기준선 적재, 공통
식별키입니다. 기술이 아니라 서면 합의로 종결되는 항목입니다.

이 네 건이 게이트의 전부는 아닙니다. 기술 설계 문서의 법무 게이트 레지스터는 22개
항목이며, 네 건은 그중 착수를 차단하는 부분집합입니다. 네 건의 종결은 적재 착수 판정을
가능하게 할 뿐, 나머지 18개 항목은 별도로 관리됩니다.

4단계는 통제 범위 밖의 결과를 포함합니다. 브로커 채널의 개방은 브로커의 결정이며, 통제
가능한 산출물은 결과 보고서까지입니다. 기존 보고 체계를 브로커가 주도하는 경우 채널
접촉이 앞 단계로 와야 할 가능성도 있으며, 이 순서는 검증 전입니다.

## 7. GTM

### 7.1 구매자

구매자는 중견기업 HR의 복리후생 담당자입니다. 갱신 비용 관리와 임직원 만족도를 함께
요구받는 자리이며, 이 프로그램은 두 과제를 같이 다룹니다. 임직원에게는 복지 항목이
추가되고, 담당자에게는 그 복지가 실제로 사용되었다는 자체 청구 기반의 근거가 남습니다.

자기부담 구조에서는 치과 비용이 기업의 직접 손익입니다. 보험료 대신 청구를 자기 계좌에서
지급하고, ASO 계약으로 지급 관리를 위탁하며, 대형 손실은 stop-loss로 별도 방어합니다.
따라서 이용 변화가 그해 비용에 반영됩니다. 치과는 대체로 stop-loss 임계값 아래 규모라
변동이 거의 그대로 기업 부담이 됩니다.

이 프로그램의 예산 항목은 검증되지 않았습니다. 플랜 관리비일 수도, 웰니스·참여 프로그램
예산일 수도 있습니다. 보고서가 아니라 프로그램으로 제안하는 이유 중 하나이기도 합니다 —
보고서는 TPA 수수료에 포함된 무료 자료와 경쟁하지만, 참여 프로그램은 별도 예산이 통상
존재하는 영역입니다. 다만 이 판단 자체가 추정이며, 실제 예산 항목은 PoC 파트너 인터뷰로
확인합니다.

### 7.1a 완전보험 기업 — 같은 프로그램, 다른 구매 논리

자기부담 한정으로 쓰면 시장을 실제보다 좁게 그리게 됩니다. 완전보험 기업도 구매 대상이며,
구매하는 것이 다릅니다.

| | 자기부담 | 완전보험 |
|---|---|---|
| 비용 반영 시점 | 당해 연도, 청구를 직접 지급 | 갱신 시점, 보험료 재산정 |
| 구매하는 것 | 비용에 개입하는 프로그램 | 갱신 협상의 근거 |
| 근거 인정 주체 | 없음 — 자기 비용 | 캐리어 — 통제 범위 밖 |
| 성과 확인 주기 | 분기 | 1년 이상 |

완전보험 기업의 논리는 다음과 같습니다. 갱신 보험료는 집단의 경험을 근거로 산정되는데,
현재 담당자에게는 집단이 개선되고 있다는 자체 근거가 없고 갱신 자료는 캐리어 측 데이터로만
구성됩니다. 참여율, 신호 분포, 청구로 확인된 예방 진료 완료는 기업이 확보하는 첫 자체
근거가 됩니다.

두 가지 제약을 명시합니다. 첫째, 캐리어가 이 근거를 인정할지는 검증되지 않았고 통제할 수
없습니다. 인정하지 않으면 근거를 확보하고도 협상 결과가 달라지지 않습니다. 자기부담에는
이 의존이 없습니다. 둘째, 완전보험은 청구 데이터 확보가 더 어렵습니다. 자기부담 기업은
자기 플랜의 청구 명세를 요구할 계약적 지위가 있지만, 완전보험의 청구 데이터는 캐리어
소유입니다.

따라서 첫 파트너는 자기부담 기업입니다. 가장 짧은 기간에 가장 적은 외부 의존으로 검증할
수 있는 구조이기 때문이며, 완전보험 시장은 그 검증 이후에 접근합니다.

### 7.2 기존 TPA 보고서와의 차이

비교 대상은 TPA 연간 보고서와 브로커 갱신 자료입니다. 무료이고, 자동으로 제공되며, 이미
신뢰받고 있고, 그 고객 관계는 브로커가 보유하고 있습니다.

비용 집계 기능만으로는 이 자료들과 차별화되지 않습니다. 같은 청구 데이터에서 산출되기
때문입니다. 차이는 청구·자격 데이터만으로는 만들 수 없는 두 항목에 있습니다.

| | TPA 보고서 (청구 + 자격) | 프로그램 (+ 신호 + 행동) |
|---|---|---|
| 확인 시점 | 진료 이후의 사후 정리 | 진료 전 신호 분포 |
| 행동 연결 | 청구와 권고의 연결 불가 | 권고 → 행동 → 청구로 확인된 완료 |

TPA 보고서의 한계 — 연 1회, 사후적, 행동과 미연결 — 이 §1 표의 왼쪽 열이며, 프로그램이
그 지점을 대상으로 합니다.

### 7.3 최소 파트너 규모

최소 셀 20명 기준이 파트너 규모의 하한을 정합니다. 대시보드의 부서 구성 기준으로
계산하면 다음과 같습니다.

| 부서 | 비중 | 20명이 되는 전사 규모 |
|---|---:|---:|
| Operations | 42% | 47명 |
| Sales | 26% | 75명 |
| Engineering | 19% | 103명 |
| Finance | 8% | 244명 |

가장 작은 비례 부서가 하한을 정하며, 계산상 244명입니다. 제안 조건의 250명은 여기에
여유를 둔 값입니다.

두 가지 전제가 있습니다. 이 계산은 부서 비중이 위 표 수준으로 고르다는 가정 위에 있으며,
실제 기업에 더 작은 비중의 부서가 있으면 하한이 올라갑니다. 데모의 `Facilities (pilot
site)` 행은 억제 화면 시연용으로 전사 규모와 무관하게 8–16명으로 고정되어 있어 항상
억제됩니다.

하한 미만 규모에서는 첫 파트너가 계약한 화면의 상당 부분을 볼 수 없게 됩니다. 첫 고객은
작을수록 좋다는 통념이 이 제품에는 적용되지 않습니다.

### 7.4 한국 실적의 의미와 한계

한국 실적은 앱·SaaS 사업의 실적이며, 임직원 복지 프로그램으로 운영한 적은 없습니다. 이
구분을 전제로 읽어야 합니다.

| | |
|---|---|
| 증명된 것 | 사람이 자발적으로 구강을 촬영한다 — 마케팅비 없이 5만 명. 참여라는 최대 미검증 가정이 앱 맥락에서 해소됨 |
| 증명된 것 | 치과가 비용을 지불한다 — 유료 치과 100곳 |
| 증명되지 않은 것 | 기업이 복지 예산으로 구매한다 — 한국 사업은 B2C·B2B2C |
| 증명되지 않은 것 | 미국 자기부담 구조에서 동작한다 — 지불 구조와 규제가 다름 |

이전되는 것은 참여가 일어난다는 사실 하나이며, 그 참여가 앱 맥락에서 복지 맥락으로
이어질지는 검증되지 않았습니다. 고용주의 권유는 참여를 높일 수도 있고, 감시로 받아들여져
낮출 수도 있습니다. 이 질문은 PoC 파트너 1곳으로 확인합니다.

기업 구매에 대한 근거는 현재 없습니다. 미국 기업 인터뷰는 §9 기준 0건입니다.

## 8. 요청 사항

### 8.1 담당자 연결

미국 HLS GTM 담당자와 아키텍처 담당자입니다. 완료 기준은 서면 후속 1건입니다.

### 8.2 PoC 파트너 소개 — 후보 3곳, 파트너 1곳

```
· 자기부담(self-funded) 치과 플랜을 운영하는 기업
· 임직원 250명 이상 — 비례 부서 기준 하한 244명에 여유를 둔 값 (§7.3)
· TPA가 Snowflake를 쓰고 같은 클라우드·리전이면 Secure Data Sharing 가능
· claim-line 데이터를 분석 목적으로 쓸 권리가 계약상 그 기업에 있는가
· 복리후생 담당자가 치과 이용 현황 파악의 어려움을 언급한 적 있는 곳
```

소개 수와 파트너 수를 구분합니다. 운영하는 PoC는 1곳이고, 요청하는 소개는 후보 3곳입니다.
조건 다섯 가운데 TPA 리전과 데이터 권리는 해당 기업이 자기 계약을 확인해야 판정할 수
있어, 소개 이후에 탈락이 확인됩니다. 후보가 1곳이면 탈락 시 90일이 표본 없이 종료됩니다.
§10.2 중단 기준의 첫 항목이 계약 파트너가 아니라 후보 수를 기준으로 하는 이유도 같습니다.

마지막 조건이 가장 중요합니다. 설득 대상이 아니라 이미 필요를 언급한 담당자를 찾고
있습니다.

명칭은 설계 파트너가 아니라 PoC 파트너로 씁니다. 요청하는 것은 제품 설계에 대한 시간
투입이 아니라, 자격·청구 데이터와 게이트 종결을 위한 법무 검토이기 때문입니다. 명칭이
기대치를 정하므로 정확한 쪽을 사용합니다.

### 8.3 계정·에디션 확인

거버넌스 기능은 에디션에 연동됩니다. 행 접근 정책, `ENTITY KEY`를 포함한 집계 정책,
마스킹, 접근 이력은 Enterprise 이상에서 제공되며, PHI 적재 단계에서는 Business Critical과
BAA가 전제입니다.

클라우드와 리전은 계정 생성 후 변경할 수 없습니다. 이전하려면 새 계정으로 복제해야 하고,
PHI 단계에서 복제는 사본을 추가로 만드는 작업이 됩니다. 에디션은 상향 가능하나 비용
구조가 바뀝니다. 따라서 우선 확인이 필요한 것은 크레딧이 부여된 계정의 현재
클라우드·리전입니다.

## 9. 현재 상태

앞의 화면들은 실행되는 코드이며, 그 이후 단계는 구축 전입니다. 구현 수준이 가장 낮은

| 앱의 데이터 분리 | 구축됨. 회원 데이터는 화면 밖 데이터 파일에만 존재, 자동 검사로 확인 |
| 동의 평가 | 구축됨. 목적·정책 버전별 기록, 사용 시점 평가, 자동 검사로 확인 |
| 근거 레이어 | 설계 완료, 미착수. 데이터 모델·정책·DDL·품질 계약·지표 시간 계약 |
| 차분 방어 | 4종 설계 완료, 미구현. 조회 축 제한만 현재 성립 |
| 사진 보존 정책 | 결정 완료, 미구현. 저장소 구축 전 |
| Core AI 호출 경로 | 계약 정의됨, 구현 없음 |
| 급여 게이트웨이 · 네트워크 디렉터리 | 없음 |
| 미국 기업 인터뷰 | 0건 |
| 절감액 | 주장하지 않음 |
| `ENTITY KEY` 검증 | 미실증. 1단계에서 합성 3사로 시험 (§4.2) |

화면 값, 문서의 주장, 계약 파일의 정의가 일치하는지는 저장소의 자동 검사로 관리하며,
변경이 반영될 때마다 실행됩니다. 실데이터를 위탁받기 전의 품질 관리 방식으로 이 체계를
제시합니다.
