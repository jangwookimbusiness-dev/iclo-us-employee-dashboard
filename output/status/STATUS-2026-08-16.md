### 이 화면의 실제 주장 셋

**분모를 섞지 않는다.** 참여는 **자격자**(834 기준)로, 비용은 **가입자-월**로 센다. 상단 렌즈 토글이 지금 어느 쪽에 서 있는지 표시하고, 두 값이 한 지표 안에서 만나지 않는다.

## 3. 임직원 앱

**화면 5개** — Home · Capture · Coverage · Find care · 설정(헤더).

### 로그인 하나에 사람 넷

기술문서 §4 의 모델을 그대로 따른다. **사람 · 계정 · 누구를 대신할 수 있는가**가 각각 다른 층이다.

```
credential ──N:M── profile_access ──N:M── party
 (로그인)          (SELF | GUARDIAN)      (사람)
```

Jordan 이 로그인 하나로 본인(`SELF`)과 자녀 둘(`GUARDIAN`)을 본다. **Sam 은 같은 플랜의 성인인데 access 가 없다** — 화면이 본인 기기에서 동의한다고, 초대가 나갔다고, 그리고 **여기에 Jordan 을 위한 컨트롤이 의도적으로 없다**고 말한다.

§4.2 는 "가족 전체 동의" 체크박스를 **배우자 데이터의 동의 근거를 무효화할 수 있는 것**이라 부른다. 단일 사용자 앱은 그 체크박스에서 UI 만 뺀 것이다.

### 사진 오귀속 방어 다섯

공유 기기에서 프로필 전환이 느슨하면 B 의 사진이 C 로 들어간다. **그 오류는 집계 화면에 절대 안 보인다** — 화면은 멀쩡하고 청구 연결만 딴 사람을 가리킨다.

1. 대상 선택 없이 촬영 시작 불가
2. **아무것도 미리 선택 안 됨** — 계정 주인조차. 공유 폰에서 그게 정확히 틀린 기본값
3. 대상자 이름이 모든 촬영 단계에서 가장 큼 + "Not Ellie — go back"
4. 흐름을 벗어나면 프로필 해제
5. 촬영자를 대상과 별도 기록

### 동의는 사람별·목적별

`데이터 처리` · `사진 촬영과 분석` · `청구 연결` 이 각각 켜지고 꺼진다. Theo 는 사진이 꺼져 있고 청구 연결은 켜져 있다 — 실제로 가능한 입장이고 스위치 하나로는 표현이 안 된다.

**철회가 실제로 무언가를 한다.** 사진이나 처리 동의를 끄면 그 프로필이 촬영 목록에서 사라지고, 촬영 중이었으면 그 자리에서 빠진다.

철회 문구는 조심해서 썼다 — 앞으로의 처리는 멈추고, 사진은 보존 일정을 따르며, **이미 배포된 집계를 다시 만들지는 아직 정해지지 않았다**고 적는다. §5.4 가 그 범위를 미결로 남겼기 때문이다.

### 예약은 넘긴다

치과 일정표에 연결돼 있지 않으므로 **빈 시간대를 모른다.** 그래서 안 보여준다. 전화(`tel:` 링크)나 그 치과 사이트로 넘기고, 웹 예약을 안 받는 곳은 그렇다고 쓴다.

넘긴 뒤에는 **묻는다** — "예약했다"는 자가 보고이고, 청구가 몇 주 뒤에 확정한다. 문구가 그렇게 말한다.

## 4. 아키텍처

```
범례   ■ 동작      ▨ 설계만      □ 설계도 없음
```

### 지금

```
        contracts/proposal-package-v11.yml  ■   정본
                     │ 손으로 옮김 ← 유일하게 남은 수동 작업
        ┌────────────┴────────────┐
        ▼                         ▼
   index.html ■              app.html ■
   상수 블록                  ACCOUNT + PARTIES
        └────────────┬────────────┘
                     ▼
              GitHub Pages ■

   fetch 0 · 백엔드 없음 · 인증 없음 · 개인정보 없음
```

### A3 — 결정됐고 미착수

```
Snowflake Enterprise ▨
  생성기 ▨ → RAW_* → STAGED → CANONICAL(20 테이블)
                                    │  R_ENGINEER 만 윈도우 함수
                                    ▼
                    mart.person_month_fact ▨   ← party_sk 보유
                      집계 정책 + ENTITY KEY
                      행 접근 정책 · 마스킹
                                    │  기업 롤은 SUM·COUNT 만
                    R_EMPLOYER_A/B/C 각각 내보내기
                                    ▼
        employer-a/b/c.json + departments.json ▨
                                    ▼
                    발행 전 검사 → git → Pages → index.html
```

**정책을 중간 테이블에 거는 이유.** 기술문서가 지시한 두 위치가 **둘 다 안 된다.** `mart.employer_overview` 에는 `party_sk` 가 없어 `ENTITY KEY` 가 성립하지 않고(있는 그대로 걸면 사람이 아니라 행을 센다), `canonical` 에만 걸면 빌드 쿼리의 `ROW_NUMBER()` 가 집계 제약에 걸려 쿼리가 실패한다. 사이에 사람 grain 테이블을 두면 둘 다 풀린다.

### 신뢰 경계

```
  개인 레벨 데이터는 존재한다  ─┐
  사진 · 점수 · 방문 · 청구      │  ICLO 안에서만
  전부 사람 단위로 저장된다     ─┘

  기업이 보는 것은 그것이 아니다
  집계 · 최소 셀 20명(고유 인물) · 밴드 · 부서 필터
```

**"집계만 저장한다" 가 아니라 "기업이 볼 수 있는 것을 제한한다" 이다.** 전자는 거짓이다 — 앱과 청구를 같은 사람으로 연결해야 "청구로 확인된 완료"가 성립하고, 그것이 이 시스템의 존재 이유다.

A3 에서 그 제한이 **JavaScript 에서 DB 정책으로** 내려간다. 그것이 A3 가 사는 이유 전부다.

## 5. 검증 체계

`.github/workflows/gates.yml` 이 push 마다 Linux 러너에서 6종을 돌린다. `concurrency` + `cancel-in-progress`.

| 검사 | 무엇을 지키나 |
|---|---|
| 레드라인 | 질환 용어 · 금지된 신호 라벨. **루트의 배포 파일과 대외 문서 포함** |
| 정본 정합성 | 6종 문서가 정본과 어긋나지 않는지 + 정본 YAML 파싱 |
| 단일 출처 | 상수를 바꿔 렌더 → 화면에 전파되는지 |
| 셀 억제 | 54 상태 → 표시값에 20 미만이 없는지 |
| 내보내기 계약 | A3 산출물이 계약을 지키는지. **없으면 PENDING, 통과가 아님** |
| fixture | 7종의 손 계산 기대값을 **입력에서 재계산** |

### 이 체계가 이렇게 생긴 이유

**조용히 죽은 검사를 세 번 찾았다.** 셋 다 "없는 것을 못 찾은 것"을 통과로 읽었다.

| 검사 | 어떻게 죽었나 |
|---|---|
| 단일 출처 | 리터럴 문자열이 안 맞게 됨 |
| 레드라인 | 배포되는 파일을 아예 안 봄 |
| 셀 억제 | 렌더 실패가 "위반 없음"으로 읽힘 |

그래서 지금 모든 검사가 같은 모양이다 — **실행이 성공했는지 확인하고, 실제로 몇 개를 봤는지 세고, 0이면 멈춘다.**

세 번째는 외부 모델(codex) 검토에서 나왔다. 그 검토를 검증하다 **내 검증 자체가 틀린 것**도 나왔다 — 존재하지 않는 경로를 가짜 브라우저로 지정해 환경변수가 무시된 채 진짜 브라우저가 돌고 있었다.

## 7. 지금 막고 있는 것

**Snowflake 계정의 에디션과 리전.** 크레딧은 이미 있다. 문제는 크레딧이 아니라 **에디션이 계정 생성 후 변경 불가**라는 것이다.

A3 종료조건 2·3 과 조회 감사 패널이 전부 Enterprise 기능(행 접근 정책, 집계 정책 + `ENTITY KEY`, 마스킹, `ACCESS_HISTORY`)에 걸려 있다.

| 답 | A3 |
|---|---|
| Enterprise 이상 + 미국 리전 | **그날 시작** |
| Enterprise + 다른 리전 | A3 는 무해. A2 전에 정리 |
| Standard | 정책을 못 쓴다. 크레딧 이전 가능 여부를 물어야 한다 |

**그 외에 코드 쪽에서 막힌 것은 없다.**

## 8. 남은 미결

**기업 수요.** 기업·브로커·컨설턴트 대화 기록 **0건**. Snowflake 대화(2026-08-14)는 파트너십(H3)이지 수요가 아니다 — 채널은 구매자가 아니다.

**앱 없이 청구만 보면 TPA 리포트와 무엇이 다른가.** `/office-hours` 이래 안 풀렸다. A3 는 거버넌스로 답을 미루고 A2 가 앱으로 답하는데, A2 에 가려면 파일럿을 설득해야 하는 순환이 있다.

**청구지연 P90 실측값.** 파일럿 전에는 합성 분포뿐이라 완료율이 "잠정" 이다.

**동의 철회의 소급 범위.** 이미 배포된 집계를 다시 만드는지. 지표 정의가 아니라 정책 결정이다.
