# Fixtures — 손으로 계산한 기대값

각 파일은 **수십 명 규모의 입력과, 사람이 손으로 계산한 결과**다. 파이프라인이 생기면
같은 입력을 태워 같은 값이 나오는지 본다.

## 왜 생성기 보정이 아니라 이 방식인가

처음 결정은 "합성 생성기를 정본 상수(PMPM $31.40 등)에 맞춰 보정하고, 그 상수와 일치하는지
검사한다" 였다. **그러면 잘못된 SQL 을 생성기 조정으로 상쇄할 수 있다.** 변환이 분모를 두 배로
부풀려도 생성기 파라미터를 반으로 줄이면 최종 숫자는 맞는다. 검사가 무력해지는 것이 아니라,
검사를 통과시키려고 오류를 두 개 만들게 된다.

고정 입력 + 손 계산 기대값에는 그 우회로가 없다. 대신 사람이 한 번 계산해야 한다.

## 왜 하나가 아니라 일곱인가

기술문서가 적어둔 **조용한 실패**들은 서로 다른 조건에서만 드러난다. 하나의 종합 케이스로는
어느 것이 깨졌는지도, 깨졌는지조차도 알 수 없다 — 오차가 상쇄되기 때문이다.

| fixture | 무엇을 잡는가 | 근거 |
|---|---|---|
| `01-baseline` | PMPM·분모 산식 자체 | — |
| `02-rehire-same-month` | `eligibility_episode_id` 기준 중복 검사 | 기술문서 783 |
| `03-retro-term` | `superseded_by IS NULL` 누락 시 분모 2배 | 783 |
| `04-two-employers` | `claims_pm` 에 `employer_id` 누락 시 타사 청구 혼입 | 1278 |
| `05-midyear-plan-change` | grain 불일치로 분자 2배 | 1274 |
| `06-idempotency` | 같은 적재 2회 → `INSERT` 면 분모 2배 | 785 |
| `07-month-length` | `30.4` 고정 제수의 3% 진동 | 1276 |

넷은 **쿼리가 성공하면서 숫자만 틀린다.** 04 는 행 접근 정책이 못 막고, 03 은 12절 중복 검사를
통과하며, 05 는 `COUNT(DISTINCT)` 가 정상으로 보이고, 06 은 재실행마다 조용히 두 배가 된다.

## 형식

```yaml
name:        무엇을 잡는지 한 줄
guards:      깨지면 이 fixture 가 빨개지는 것들
input:
  eligibility_spans: [...]     # 자격 기간
  claims:            [...]     # 청구 라인
expected:
  member_months:  손 계산값
  dental_pmpm:    손 계산값
  working:        어떻게 그 수가 나오는지 — 다음 사람이 재계산할 수 있게
```

`working` 은 장식이 아니다. 기대값이 틀렸을 때 **입력이 틀린 것인지 계산이 틀린 것인지**
구별하는 유일한 방법이고, 그것 없이는 파이프라인이 아니라 fixture 를 고치게 된다.
