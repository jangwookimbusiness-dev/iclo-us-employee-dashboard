
**정책을 `person_month_fact` 에 거는 이유.** 기술문서가 원본(§10.3)과 산출물(§11) 두 곳을 지시했는데 둘 다 그대로는 안 된다. `mart.employer_overview` 에는 `party_sk` 가 없어 `ENTITY KEY` 가 성립하지 않고, `canonical` 에만 걸면 `employer_overview` 빌드의 `ROW_NUMBER()` 가 집계 제약에 걸려 쿼리가 실패한다. 사이에 사람 grain 테이블을 두면 둘 다 풀린다.

**여기서 바뀌는 성질 셋.**

1. `render()` 가 **계산에서 조회로** 바뀐다. 지금은 전사 값에 비율을 곱해 부서 값을 만들고, 그때는 `GROUP BY` 결과를 찾는다
2. **억제 판정이 서버로 간다.** `index.html:290` 의 `D.n < 20` 이 죽고, NULL 키 remainder 를 억제로 렌더해야 한다
3. **`file://` 가 끝난다.** `fetch` 가 생기는 순간 CORS 로 막혀 `scripts/serve.sh` 가 필요해진다

## 신뢰 경계 — 이 문서의 요점

```
  개인 레벨 데이터는 존재한다.  ─┐
  사진 · 점수 · 방문 · 청구 라인 │  ICLO 안에서만
  전부 사람 단위로 저장된다.     ─┘

  기업이 보는 것은 그것이 아니다.
  집계 · 최소 셀 20명(고유 인물) · 밴드 · 부서 필터.
```

**"집계만 저장한다" 가 아니라 "기업이 볼 수 있는 것을 제한한다" 이다.** 전자는 거짓이다 — 앱과 청구를 같은 사람으로 연결해야 "청구로 확인된 완료" 가 성립하고, 그것이 이 시스템의 존재 이유다.

A3 에서 그 제한이 **JS 에서 DB 정책으로** 내려간다. 그것이 A3 가 사는 이유 전부다.
