## v2가 낫고 v1이 놓친 것

**`SYNC-06`을 v2가 닫았다.** 정본 `open_items`에 "대시보드 화면 이름·KPI 이름이 Report·Proposal 어디에도 등장하지 않는다"가 미해결로 올라 있고, 처방은 "각 문서의 대시보드 절에서 `dashboard.tabs`·`dashboard.kpis` 라벨을 그대로 인용"이다.

v2는 `Overview` / `Signals` / `Funnel` 탭과 `Eligible employees`, `Activated (registered + first questionnaire)`, `Valid capture (passed photo-quality gate)`, `Open care actions`, `Completed actions`, `Repeat participation` 여섯 KPI 라벨을 표로 그대로 실었다. v1은 시나리오 수치와 신호 분포만 인용하고 라벨을 쓰지 않았다. **v1의 결함이다.**

**`SYNC-08`도 v2 쪽이 낫다.** "self-funded 설명이 나오는 곳마다 ASO·stop-loss를 세트로"가 처방인데 v2는 4회, v1은 2회다. v2는 `self-funded / ASO / stop-loss`를 아예 한 덩어리 제목으로 썼다.

**출처를 본문에 붙였다.** v2는 DOL·ADA·NHIS 링크를 주장 옆에 직접 달았다. v1은 부록에서 `Sources-v10.md`로 미룬다. 비기술 임원이 회의 중에 근거를 확인하려면 v2 방식이 낫다.

## v1이 낫고 v2가 놓친 것

**"왜 Snowflake인가"가 v2에 사실상 없다.** v1은 기업 간 격리(행 접근 정책), 최소 셀의 DB 강제, 데이터 권리 협상에서의 Secure Data Sharing 세 가지로 절을 따로 뒀다. v2는 게이트 절 끝에 "플랫폼 설정만으로 닫히지 않는다" 한 줄뿐이다. **읽는 사람이 Snowflake Korea인데 이건 크다.** 이 문서가 그 사람에게 주는 사내 명분이 여기서 나온다.

**문체 등급.** v1은 `~습니다`, v2는 `~다`. 임원에게 보내는 제안서는 `~습니다`가 맞다. v2의 평서체는 기술 문서 어조라 요청 문서로는 거리감이 있다.

**진입 설계.** v1은 0절에 "15분 걸리지만 판단은 셋"과 위치 표를 뒀다. v2는 요청부터 바로 들어간다. 요청을 먼저 놓는 건 좋지만, 비전문가에게 "어디를 읽으면 되는지"를 주는 장치가 없다.

**청구 지연 설명.** v1은 2.4절에서 "이번 달 숫자는 아직 완성되지 않은 숫자"와 퇴사자 run-out까지 풀었다. v2는 48행에서 "청구는 진료 직후 한꺼번에 확정되지 않으므로" 한 문장이다. 이 시장을 모르는 사람에게는 v1 분량이 필요하다.
